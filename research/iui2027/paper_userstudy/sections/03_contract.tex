\section{Interaction Contract}
\label{sec:contract}

Software contracts usually guard technical boundaries.  In an intelligent
interface, the same decisions also determine what the user may see, which agent
may respond, and where correction remains possible.  We use one running
scenario throughout: a visitor selects \texttt{brand\_panel3} while the Lounge
Host is active.  The system must preserve that target, resolve the responsible
agent, enforce any permitted handoff, invoke the declared capability, and
present an answer only while the resulting target--agent relation remains
intact.

\subsection{Failure model and intelligibility mapping}

A fluent response can mask an unknown target, ambiguous responsibility, a
forbidden handoff, or evidence for another object.  Following the
intelligibility questions established by Lim and Dey and later question-driven
XAI work \cite{lim2009demand,liao2020questioning}, we organize the contract
around \emph{What}, \emph{Why}, \emph{Why not}, and \emph{How to}.  The
prototype does not currently expose interactive \emph{What if} alternatives.
Reference, responsibility, capability, and outcome transparency are therefore
not a new explanation taxonomy; they identify which typed contract state can
answer which established user question.

\subsection{Contract objects and executable path}

A contract-grounded interaction is represented by
\[
\mathcal{I} =
\langle m,s,t,p,u,c,b,a,q,o\rangle ,
\]
where \(m\) is the pinned model and hash, \(s\) the scenario step, \(t\) the
target, \(p\) the provider, \(u\) the capability use, \(c\) the capability,
\(b\) the runtime binding, \(a\) the concrete action, \(q\) the assertions, and
\(o\) the observation evidence.  The tuple groups the state required by the
four transparency types: \(t\) supports reference, \(p\) responsibility,
\(u,c,b,a\) capability, and \(q,o\) outcome transparency.  In the running
example, \(t\) is \texttt{brand\_panel3}, \(p\) is the Reception Agent, and the
remaining elements declare and verify its grounded-answer action.

The required declaration path is
\[
s \rightarrow u \rightarrow c \rightarrow b \rightarrow a.
\]
A step cannot invoke \(a\) directly.  Its capability use must name the trusted
target and provider and resolve exactly one capability, binding, and action.
Thus, a generic \texttt{POST /chat} call cannot bypass the declaration that the
Reception Agent may answer about this panel.

The provider is resolved independently of display names.  For target \(t\), the
resolver selects the most specific non-empty responsibility tier:
\[
R(t) =
\begin{cases}
R_{\mathrm{asset}}(t), & \text{if non-empty},\\
R_{\mathrm{group}}(t), & \text{otherwise if non-empty},\\
R_{\mathrm{zone}}(t), & \text{otherwise}.
\end{cases}
\]
Exactly one agent at the selected tier is required.  This is a deterministic
specificity policy, not a claim about which agent visitors intuitively expect:
an asset-level owner overrides group and zone defaults.  For
\texttt{brand\_panel3}, the policy selects the Reception Agent; if the Lounge
Host is active, one declared handoff may reach it.  Because this result can
differ from the nearest or active agent, the interface exposes the selected
provider and handoff rather than requiring users to infer the hierarchy.

\subsection{Admission and response conditions}

A deictic request is admitted only if:

\begin{enumerate}
  \item the session is pinned to \(m\), and its hash matches the current project
  and stored contract fingerprint;
  \item entity and source identifiers resolve to the same unique target \(t\),
  with a resolved, non-ambiguous selection state;
  \item \(R(t)\) yields exactly one provider \(p\), which is either active or one
  permitted direct handoff away;
  \item one capability use \(u\) resolves to exactly one capability \(c\),
  binding \(b\), and action \(a\); and
  \item the request conforms to the declared action schema.
\end{enumerate}

Conditions 1--2 establish reference transparency (\emph{What}); Condition 3
establishes responsibility transparency (\emph{Why}/\emph{Why not}); and
Conditions 4--5 establish capability transparency
(\emph{Why not}/\emph{How to}).  For the running example, they confirm the room
and panel, resolve the Reception Agent, permit the Lounge Host's direct handoff,
and select the grounded-answer action before generation.  The returned proposal
is then checked against \(q,o\): mismatching identifiers or an undeclared
handoff are rolled back, whereas agreement establishes outcome transparency
(\emph{What}) and permits presentation.

\subsection{Guarantee boundary}

The contract guarantees model consistency: an admitted request has one trusted
target, one declared provider reachable by at most one handoff, one
capability-to-action path, and matching response evidence.  The same relations
support answers to the implemented \emph{What}, \emph{Why}/\emph{Why not}, and
\emph{How to} questions, but they do not guarantee that the visitor intended
the selected collider, that generated content is factually correct, or that the
chosen cues improve comprehension or calibrated trust.  The user study
therefore tests the concrete mapping through target-selection clarity,
answer--target fit, handoff understanding, final-agent clarity, perceived
responsibility, predictability, guidance, and overall ease.
