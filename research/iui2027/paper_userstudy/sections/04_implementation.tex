Here we show how they become visitor-facing state: a retained target highlight,
an observable handoff, capability guidance, and either a grounded answer or a
recoverable rejection.  Figure~\ref{fig:functionalmlds-core} follows one
request in the cheese booth, where the Reception Agent hands a question about

\subsection{Interaction state in FunctionalMLDS}

A Meta-Language-defined Structure (MLDS) is a machine-readable artifact whose
vocabulary and structural rules are defined by an explicit meta-language
specification \cite{fischer2025machinereadable}.  Each room-specific
FunctionalMLDS document is such an instance.  For the interface, its practical
purpose is to provide one authoritative relation chain: which spatial entity
was selected, which agent is responsible, which capability may be used in the
current scenario, which runtime action realizes it, and which evidence is
required before an answer may be shown.  Visitors do not see these metamodel
elements or identifiers directly; they see the projection summarized in
Figure~\ref{fig:functionalmlds-core}.

The conceptual foundation is the UML use-case and scenario view: actors
participate in use cases, and scenarios refine a user-visible goal into ordered
steps.  The repository realizes this foundation with selected EAST-ADL 2.1.12
elements and associations, including \texttt{UseCaseDefinitionSet},
\texttt{UseCaseDefinition}, and \texttt{UseCase}, together with requirements
and verification concepts \cite{eastadl2013spec}.  FunctionalMLDS does not
claim complete UML or EAST-ADL conformance.  It extends this foundation with
the information required by a spatial multi-agent interface: stable entities,
agent responsibilities and handoffs, scenario-specific capability uses,
runtime actions, and expected evidence.

The distinction between a reusable capability and its use in one interaction
is central.  ``Answer grounded questions'' is a capability; ``the Product
Specialist Agent answers about \texttt{refrigerated\_counter1} in this step''
is a capability use.  The latter binds a visible target and responsible agent
to the executable path.  This is what lets the interface retain the selected
counter, disclose a provider change, and state that an operation is unavailable
instead of routing a generic chat request.

\subsection{Validation as an interface boundary}

Validation is organized as four gates, each protecting a state that may later
become visible.  \textbf{Serialization validation} checks required fields,
types, and reference shapes so that malformed room data never enters the
interaction.  \textbf{Model validation} checks referential closure,
cardinalities, unique source identifiers, valid assertion ownership, and the
absence of direct scenario-step-to-action shortcuts; this prevents target and
provider cues from being derived from contradictory relations.
\textbf{Executable-profile validation} requires one provider and capability per
evaluated capability use, agreement among provider, performer, and target
responsibility, and a complete runtime binding; an incomplete interaction is
therefore marked unavailable rather than guessed.  \textbf{Runtime validation}
then binds one request and response to one already valid, pinned instance and
blocks stale or mismatching output before presentation.

Room objects are identified by stable \texttt{id} and \texttt{sourceId} values,
not by display labels or 3D-engine names.  Agents likewise have unique source
identifiers and typed references to capabilities, responsibilities, grounded
objects, and handoff targets.  The canonical instance remains authoritative;
client and backend projections contain only the subset they need.  As a result,
visible labels can change without silently changing which object or agent the
interaction contract addresses.

\subsection{Authoring and safe publication}

The generation pipeline is not part of the visitor's interaction, but it
determines whether a room is made available as a coherent interactive space.
Structured room data and frozen semantic artifacts are transformed into
objects, groups, zones, agent roles, handoffs, scenarios, capability uses,
runtime bindings, assertions, and validation cases.  Deterministic stages
assign stable identifiers and derive the client trace map and backend runtime
context.  All validators must pass before publication, and content hashes bind
the canonical model to both projections.

This publication boundary has a direct interaction consequence: an outdated
client, backend configuration, or partially regenerated room is rejected during
setup rather than being allowed to produce an answer under a different target
or responsibility model.  Language models may propose scene semantics, role
labels, handoffs, and knowledge during authoring, but they do not choose runtime
identifiers, decide routes, or override failed structural checks.  Once these
semantic artifacts are frozen, the complete model can be regenerated and
tested without a network or model API.

\subsection{3D-client selection and visible state}

The evaluated client is implemented in Unity, but the binding principle is
engine-independent: every selectable scene object must map to exactly one
stable model entity.  In the desktop interaction, a camera ray selects a
registered collider.  The client marks the object with a spatial highlight and
retains that target while the visitor composes the request.  It distinguishes
\texttt{none}, \texttt{resolved}, and \texttt{ambiguous} selection states.  Only
a resolved state enables a deictic request; the other states remain visible and
lead to guidance rather than an inferred target.

A scene-object component binds each relevant collider to an exact entity and
source identifier.  During startup, the registry rejects duplicate entities,
duplicate source matches, conflicting manual bindings, and missing
target-specific contexts; UUID-like suffixes are not accepted as approximate
matches.  The request carries the pinned model hash, entity and source
identifiers, candidate list, hit position and distance, input modality, active
agent, and utterance.  Numeric ranges, list sizes, and string lengths are
bounded.  The backend repeats the authoritative identity check rather than
trusting the client alone.

Figure~\ref{fig:unity-selection} shows the same binding mechanism on another
object in the booth.  The selected source object \texttt{brand\_panel3} is
bound to \texttt{ENT-ASSET-BRAND\_PANEL3}.  The running cheese-counter
interaction uses the same exact entity/source-ID path; the screenshot is a
committed desktop capture rather than a headset study or a finished diagnostic
interface.

The client bridge does not dispatch a generic ``chat'' operation.  It uses the
selected entity and server-resolved provider to find the target-specific
scenario context, then accepts only the scenario, capability, binding, and
action identifiers confirmed by the backend.  Zero or several exact contexts
leave the interaction unresolved and fail closed.

\subsection{Authoritative routing, execution, and recovery}

At session setup, the backend validates the native V2 instance and trace map,
builds the runtime context, and pins the model hash and contract fingerprint.
If any artifact changes, the session must be set up again with the regenerated
model rather than adopting the change silently.  For each request, the backend
rejects malformed or stale spatial payloads, including conflicting identifiers,
unknown scene objects, ambiguous candidates, invalid active agents, and
non-finite or out-of-range ray values.  It derives the selected asset's group
and zone from the pinned model instead of trusting client-provided
responsibility information.

Responsibility resolution then applies the asset--group--zone precedence from
Section~\ref{sec:contract}.  The active agent may answer locally or hand off
once along a declared edge.  When another provider is selected, that change is
returned as explicit interaction state for the handoff cue.  When no permitted
provider exists, the request is rejected with relation-specific guidance rather
than silently reaching a different agent.  The backend next resolves one exact
runtime action from the trusted scenario, provider, and target; a matching
generic endpoint or action kind is insufficient.

Before generation, the backend snapshots mutable session state.  A
request-decidable failure therefore stops before a response-model call and
leaves the conversation unchanged.  A failure that can be known only after
generation---for example an undeclared handoff or mismatching returned
identifier---restores the snapshot and suppresses the output.  Thus a fluent
response is never presented merely because the model call itself succeeded.

\subsection{Evidence, feedback, and diagnostics}

The runtime trace serves two audiences.  For presentation, the client compares
the returned target, provider, route, binding, and action with its pending
selection and the admitted contract path.  Matching evidence permits the answer
to be shown while retaining the responsible-agent state; a mismatch produces
rollback or corrective guidance.  For diagnosis, the accepted response and
runtime events additionally retain the model hash, scenario and step,
capability use, capability, assertion references, and observation verdicts.
Missing observations can remain \texttt{inconclusive} instead of silently
passing.

The visitor interface applies the progressive disclosure described in
Section~\ref{sec:contract}: it exposes the selected or unresolved target, makes
a provider change observable through the evaluated handoff state, and displays
concise status or guidance when the request cannot proceed.  Internal
identifiers, exact route reasons, bindings, and assertion records remain in
logs and runtime components.  The user study evaluates this lightweight cue
mapping; richer explanations and persistent responsibility panels are not
implemented or compared.

\subsection{End-to-end walkthrough}

The running interaction now follows a concrete visitor path.  First, the
visitor explores the booth, selects the refrigerated cheese counter, and keeps
its highlight while asking, ``What cheese is displayed here?''  Second, the
client submits the counter's exact identifiers together with the currently
active Reception Agent.  Third, the backend resolves the Product Specialist
Agent from the asset-level responsibility relation, verifies the declared
direct handoff, and returns that provider change for the interface to expose.
Fourth, it invokes only the grounded-answer action declared for this target and
provider.  Finally, the answer is presented only when its evidence still names
the same counter, provider, route, and action; otherwise the provisional state
is restored and guidance is shown.  Starting the same request from the Lounge
Host would require two handoff edges through the Reception Agent, so it is
rejected before generation and the conversation remains unchanged.
